# Agent notes

## Project
Interactive Mars map for astronauts and mission planners: 4 stacked layers (base imagery, relief/walkability, points of interest, seasonal dust-storm risk) for a single demo area (East Melas / Coprates Chasma, Valles Marineris), plus a route planner over a master graph that combines all layers.

## Architecture rules
- **The frontend consumes ONLY our FastAPI backend**, never NASA/Harvard servers directly. The backend owns the response format of every layer (tiles, GeoJSON, route) so different sources look uniform to the client.
- **Static local data (MVP):** `scripts/download_data.py` is a one-off setup step -> `data/raw/` (gitignored) -> backend layer getters + master graph -> API -> React. The backend serves every layer directly from the downloaded files. **No external API calls, proxy or cache at runtime** (backend or frontend). Don't download datasets by hand; to get more data, extend the download script and re-run it.
- **Backend:** FastAPI. Four independent layer endpoints + one route endpoint. Each layer has an ingestion module (`app/layers/<layer>/`) that outputs normalised data on a shared `GridSpec`; the graph builder consumes only that output, never `data/raw/` directly.
- **One master graph, two profiles (`astronaut`, `car`).** Same topology; every directed edge stores per profile a routing `cost` plus resource use (`time_s`, `o2_g`, `co2_g`, `water_g`, `energy_wh`) as struct-of-arrays (not a dict per edge). Graph and costs are flat NumPy arrays; SciPy (`csgraph.dijkstra`) for paths; destinations are visited in the order the user entered them (`app/routing/sequence/`). Season is a request parameter, not part of the graph or the cost; weather only produces warnings. Slope shown to users and slope used by the router must come from the same array.
- **Parallel work:** code against the contracts and the synthetic fixtures (`app/layers/fakes.py`), not against another module's real implementation. Changing a contract means editing the reference doc in the same PR.
- **Frontend:** React + Vite + Leaflet (`react-leaflet`) with `L.CRS.EPSG4326` (Mars tiles are plain lat/lon, not Web Mercator).
- **Data-sufficiency rule (mandatory):** where a layer frame lacks enough data, the UI must say so explicitly; approximate values must be labelled as approximate. Render the weather `message` field verbatim.

**Shared contracts already exist (step 0, tested):** `app/core/{resources,profiles}.py`, `app/core/configfile/` (loads `config/mars.yaml`, the one file for profile parameters, budgets, slope classes and routing limits), `app/layers/{contracts,fakes,validate}.py`, `app/layers/relief/slope.py`, `app/graph/contracts.py` (`GraphData`), `app/routing/contracts.py`, `app/schemas/{route,layers}.py`. Import from these; do not redefine them. **Routing engine (package G) is done:** `app/routing/{graph,matrix,solver,assemble,service}.py` (flat NumPy arrays plus SciPy CSR matrices and `scipy.sparse.csgraph.dijkstra`, no per-edge Python objects), entry point `plan_route` (SKILL.md section 10, "Implementation"). Routing is terrain-aware: edges are impassable where the map slope of either end cell exceeds the profile limit, roughness raises the cost, dune fields block the car and slow walking, RSL sites are blocked within `hazards.rsl_buffer_m` (edge-cost-model.md section 4a). `POST /api/route` defaults to `"profile": "auto"` (picks walking or driving: reach, then oxygen per person, then time; `app/routing/modes/`) and accepts start + end without destinations (point-to-point). **Graph (work package F) is built and tested:** `app/graph/{edges,geometry,attrs,nodes,build,store,loader,cli,fakes}.py`; real per-profile formulas are in `app/routing/profiles/` (all parameters still placeholders). The real graph is built automatically when the API starts if it is missing or stale (`routing.build_graph_on_startup` in `config/mars.yaml`; background thread in `app/graph/startup/`, `/api/route` is 503 until it is ready; first start ~1 min and ~4 GB). To build it by hand: `cd backend && python -m app.graph` (inputs from `app/layers/inputs/load.py: load_all`, on the native 200 m grid by default, `Settings.grid_coarsen`; writes `data/graph/graph.npz`, about 40 s and 490 MB), or a dev graph with `--fake`. At startup `app/graph/loader.py: load_routing_context(settings)` loads it into a `RoutingContext` (the `RoutingGraph` plus a KD-tree for snapping). The API controllers exist (`app/api/routes/{layers,tiles,route}.py`, `app/routing/{request,snap}.py`); `POST /api/route` requires login (401 otherwise), answers 503 until the graph is ready, and estimates the astronaut's oxygen, CO2 and water for the requesting user's stored body mass (the route itself never depends on it). End-to-end tests: `backend/tests/integration/test_graph_integration.py` (layers -> graph -> `plan_route`) and `test_pipeline_api.py` (data -> `python -m app.graph` -> app startup -> `POST /api/route`, cross-checked against the layer endpoints; the real-data part builds the native graph, about a minute). Everything else is still an empty placeholder (`.gitkeep`) beyond the Vite and FastAPI starters.
The four layers follow `references/layer-ingestion.md`: `ingest.py` + `service.py` per layer (the service classes are still called `...Getter`), endpoints are the implemented `/api/get-layer-*` paths (listed in the reference, section 6), POI features carry `kind` and `category`, weather data lives in `data/raw/weather/` (computed by `scripts/weather/` through `download_data.py --only weather`). Auth is done: JWT + SQLite users with body mass and birth year (`app/auth/`, `app/db/`, `/api/auth/*`, `/api/users/me`; SKILL.md section 10a). Still missing: the frontend. Design notes of the earlier getters: `docs/superpowers/specs/2026-11-14-layer-getters-design.md` (its section 7a lists differences that are now settled).

## Commands
- Data: `pip install -r scripts/requirements.txt && python scripts/download_data.py` (`--only dem|tiles|pois|mdad|weather`, `--max-zoom N`, `--force`). The `weather` step computes the static weather layer into `data/raw/weather/`. Pipeline tests: `cd scripts && pytest`.
- Backend tests: `cd backend && pip install -r requirements.txt && pytest`.
- Configuration: edit `config/mars.yaml` (profile parameters, budgets, slope classes, routing limits; each section is `placeholder` until confirmed with a source); `MARS_CONFIG` or `--config` selects another file; rebuild the graph after changing a profile parameter, and re-run `download_data.py --only weather --force` after changing the weather risk thresholds. The API logs a stale graph or stale weather files at startup.
- Backend: see README (uvicorn on :8000; needs `JWT_SECRET_KEY`, copy `backend/.env.example` to `backend/.env`). Frontend: see README (Vite on :5173, proxies `/api/*`).

## Development rules (all agents; full text in SKILL.md section 11)
- **Whenever you create new code, put it in a subdirectory named after the module, and create that directory if it does not exist.** Backend: `backend/app/<module>/` (with `__init__.py`). Frontend: `frontend/src/<area>/<Module>/`. Scripts: `scripts/<module>/`. No loose files at a package root.
- **Add tests for all code you write, in the same change.** Backend: pytest, mirroring the module path in `backend/tests/<module>/test_<file>.py`, run with `cd backend && pytest`. Frontend: Vitest + React Testing Library with `<Name>.test.jsx` next to the source, run with `cd frontend && npm test` (`react-leaflet` is replaced by `src/test/reactLeafletMock.jsx` in tests; see `frontend/README.md`).
- Tests are offline and deterministic: use the fixtures in `app/layers/fakes.py` and tiny hand-built graphs; tests needing the real `data/raw/` files skip when it is missing.
- Run the tests before finishing and report failures honestly.
- Update the matching doc (`references/*.md`, SKILL.md, this file) in the same change when you alter a contract, formula, endpoint or folder.
